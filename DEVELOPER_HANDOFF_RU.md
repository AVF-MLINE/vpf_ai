# Передача задачи разработчику

## Что это за задача
Нужно добавить в Rails-проект новую справочную колонку: `Группа риска по ИИ`.

Сейчас в проекте уже есть:
- группа риска по алгоритму;
- итоговая группа врача.

Нужно рядом показывать ещё и результат ИИ.

Важно:
- ИИ не заменяет алгоритм.
- ИИ не заменяет решение врача.
- ИИ работает только как справочная оценка.
- Расчёт должен выполняться в фоне и не тормозить интерфейс.

## Что уже подготовлено
В репозитории уже лежит готовый каркас:

- схема факторов и whitelist полей:
  - [`config/factor_schemas.yml`](./config/factor_schemas.yml)
- Ruby-библиотека для сборки payload и вызова Yandex:
  - [`lib/`](./lib)
- шаблоны файлов для Rails:
  - [`templates/rails/`](./templates/rails)
- инструкция по подключению:
  - [`README.md`](./README.md)

## Что нужно получить от заказчика или аналитика
Перед началом работы нужны такие данные:

1. Где в Rails-коде находится модель заключения врача-профпатолога.
2. Где сейчас строится таблица “Оценка группы риска”.
3. Какие фоновые задачи используются в проекте:
   - `Sidekiq`
   - `GoodJob`
   - `Delayed Job`
   - другое
4. Доступы к Yandex AI Studio:
   - `YANDEX_AI_API_KEY` или `YANDEX_AI_IAM_TOKEN`
   - `YANDEX_AI_FOLDER_ID`
5. 5-10 обезличенных реальных примеров на каждый фактор:
   - ВБО
   - ВБЛ
   - НСТ
   - ХОБЛ
6. Подтверждение, что в Yandex можно отправлять только обезличенные данные.

## Что нужно сделать по шагам

### Шаг 1. Подключить каркас в Rails
- Скопировать папки `lib/` и `config/factor_schemas.yml` в Rails-проект.
- Скопировать нужные файлы из `templates/rails/`.

### Шаг 2. Создать таблицу для результатов ИИ
- Добавить миграцию `ai_risk_assessments`.
- Выполнить миграцию.

В таблице должны храниться:
- `conclusion_id`
- `factor_code`
- `ai_group`
- `confidence`
- `status`
- `classifier_version`
- `payload_snapshot_json`
- `requested_at`
- `completed_at`
- `error_code`
- `error_message`

### Шаг 3. Привязать к модели заключения
- Подключить concern `AiRisk::ConclusionSource`.
- Реализовать метод `to_ai_risk_inputs`.

Этот метод должен собрать обычный Ruby hash из данных заключения в формате, который ожидает `config/factor_schemas.yml`.

### Шаг 4. Сделать маппинг полей
Нужно замаппить реальные поля проекта на `source_path` из YAML.

Пример:
- если в проекте данные кашля лежат в одном месте, а в YAML указано `index_mmrcs.has_cough`, значит в `to_ai_risk_inputs` нужно положить значение именно по этому пути.

Смысл такой:
- реальные данные проекта -> привести к единому hash -> передать в `VpfAi::Assessor`.

### Шаг 5. Настроить Yandex
- Прописать переменные окружения:
  - `YANDEX_AI_API_KEY` или `YANDEX_AI_IAM_TOKEN`
  - `YANDEX_AI_FOLDER_ID`
- Убедиться, что логирование запросов отключено.
- Убедиться, что отправляются только обезличенные данные.

### Шаг 6. Запускать расчёт в фоне
- После сохранения заключения ставить задачу в background job.
- Не считать ИИ в web-request.
- Если Yandex временно не отвечает, сделать 2-3 повтора.
- Если всё равно ошибка, просто сохранить статус ошибки и не ломать сохранение заключения.

### Шаг 7. Считать отдельно 4 фактора
Для каждого заключения запускать расчёт по:
- `vbo`
- `vbl`
- `nst`
- `hobl`

Если по какому-то фактору не хватает обязательных данных:
- не угадывать;
- сохранять статус `insufficient_data`.

### Шаг 8. Добавить результат в API
Нужно отдать в API или serializer:
- `ai_risk_group`
- `ai_risk_status`

Достаточно итоговой группы:
- `I`
- `II`
- `III`
- `IV`

Если расчёт не готов или не удался:
- вернуть пустое значение или статус `нет оценки`.

### Шаг 9. Добавить колонку в интерфейс
В таблице “Оценка группы риска” добавить колонку:
- `Группа риска по ИИ`

Правила показа:
- если `status = completed`, показать группу;
- если `pending`, `error` или `insufficient_data`, показать пусто или `нет оценки`.

На первом этапе не показывать:
- confidence;
- текстовое объяснение;
- key factors.

### Шаг 10. Проверить на реальных кейсах
Минимум проверить:
- по 1-2 кейса на каждый фактор;
- успешный расчёт;
- кейс с нехваткой данных;
- кейс с ошибкой провайдера;
- повторный пересчёт после обновления заключения.

## Что считается готовым
Задача считается выполненной, если:

1. После сохранения заключения запускается фоновый расчёт ИИ.
2. Для 4 факторов сохраняются результаты в БД.
3. В интерфейсе появляется колонка `Группа риска по ИИ`.
4. ИИ не влияет на алгоритм и не влияет на итог врача.
5. При нехватке данных сохраняется `insufficient_data`.
6. При ошибке Yandex интерфейс и сохранение заключения не ломаются.

## Что важно не забыть
- Не отправлять ФИО.
- Не отправлять дату рождения.
- Не отправлять табельный номер.
- Не отправлять подразделение, если это не нужно для расчёта.
- Не отправлять свободный текст врача в MVP.
- Не делать синхронный вызов ИИ из контроллера.

## С чего начать разработчику
Самый правильный порядок:

1. Поднять миграцию и модель `AiRiskAssessment`.
2. Подключить `to_ai_risk_inputs` к модели заключения.
3. Замаппить поля для одного фактора, например `ХОБЛ`.
4. Прогнать end-to-end на одном факторе.
5. После этого добавить оставшиеся 3 фактора.

Так будет быстрее и безопаснее, чем пытаться сразу внедрить все 4 без промежуточной проверки.
